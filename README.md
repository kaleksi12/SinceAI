# Digital Security Assistant: "What should I do now?"

**Badger Squad** · DNA challenge at Since AI Hackathon 2026

An assistant that lives inside a telecom operator's app. A consumer or a small-business user describes something worrying (a text, a call, a link they clicked, a breach notice, an odd order on the company account) and gets **one clear, proportionate next step**: what to do, why, how urgent it is, and a handoff to a human when needed. It asks only for facts that change the advice, asks for consent before looking at private data, and answers in Finnish, English or Swedish.

**Result on the organisers' 588 dev cases (single-turn):** 86.6 % safe-action pass (95 % CI 83.5–89.1), against 60.5 % for the organisers' rules baseline. Weighted scorecard proxy 88.6 / 80 automated points. Unsafe statements: 0.9 % (5 answers, all an "block your card" when no card was involved).

**Multi-turn (conversations with the organisers' simulated user, same 588 cases):** 86.2 % safe-action pass, false alarms on benign cases 4.5 % (10.6 % single-turn), unsafe statements 0.2 %, weighted proxy 88.9.

Details, failures and limitations are in [`RESULTS_REPORT.md`](RESULTS_REPORT.md).

> Prototype. All data is synthetic, and the advice is generated by AI from the organisers' synthetic guidance. It is not official DNA advice.

## How it works

1. **Analysis (LLM).** Reads the user's words and the visible signals and fills in yes/no/unknown facts: was a code shared, was money sent, did the user start this change themselves, and so on.
2. **Safety rules (code, `assistant/rules.py`).** Turn those facts into limits: a forced action, a minimum risk level, a human handoff, and which decisive questions are still worth asking. The rules can only make the answer more cautious.
3. **Writer (LLM) and checks.** Writes the advice for the decided action. The organisers' text checks reject unsafe claims, jargon and the wrong language; on a second failure a ready-made template is used.

The same pipeline produces the single-turn submission and powers the live chat. The live chat (`assistant/dialogue.py`) adds:
- routing of small talk, general questions and follow-ups, so only real incidents get a full advice card;
- replies in the language of the user's latest message, in plain words without technical jargon;
- a consent request (Allow / Not now) before private signals are used.

### Safety boundaries
- Text inside forwarded messages is treated as untrusted data, so prompt-injection lines in a scam message are ignored.
- The assistant never asks for passwords, codes, PINs or card numbers.
- Every reply is checked against a list of unsafe advice ("pay the fee", "approve the prompt", ...).
- Consent-gated signals are hidden by code until the user allows them; the model cannot see them otherwise.
- The assistant only gives advice. It takes no actions, and the handoff to a human is simulated in this prototype.

## Repository layout

| Path | What it is |
|---|---|
| `assistant/` | The assistant: `rules.py` (safety rules), `bot.py` (pipeline), `prompts.py` (LLM prompts), `dialogue.py` (live chat), `api.py` (FastAPI backend), `llm.py` (LLM client with a local cache) |
| `frontend/` | React web app (operator-app style chat UI, built with Lovable) |
| `scripts/run_single.py` | Runs the assistant over a case file, then evaluates and validates the result |
| `runs/` | Our result runs: predictions, evaluator reports, run metadata |
| `tests/` | Unit tests (LLM calls are mocked) |
| `simset/` | The organisers' kit (data, evaluator, simulator), used as is and not edited |
| `test_predictions.jsonl` | Our submission: single-turn answers for all 335 test inputs |

## What you need

- **Python 3.10+** and **Node.js 20+** (for the frontend).
- **An LLM API key.** We use `deepseek-ai/DeepSeek-V3.1` through [Featherless](https://featherless.ai). Any OpenAI-compatible API also works: set `FEATHERLESS_BASE_URL` and `LLM_MODEL` in `.env`.
- Our own key is not included. **Without a key** you can still run the unit tests, score our committed runs with the organisers' evaluator, and validate the submission file (see [Reproduce our results](#reproduce-our-results)).

The commands below are for **Windows (PowerShell)**. On **Linux / macOS**, use `python3` instead of `python` and `cp` instead of `copy`.

## Setup

In the repository root:

```powershell
pip install -r requirements.txt
copy .env.example .env
```

Open `.env` and put your key after `FEATHERLESS_API_KEY=`.

Install the frontend packages once:

```powershell
cd frontend
npm install
cd ..
```

## Run the app

Use two terminals.

**Terminal 1: backend** (in the repository root)
```powershell
python -m uvicorn assistant.api:app --reload --port 8000
```

**Terminal 2: frontend** (in the `frontend` folder)
```powershell
cd frontend
npm run dev
```

Open <http://localhost:8080/>. The frontend forwards `/api/...` calls to the backend on port 8000.

- **Start from:** choose free text (consumer or small business), or one of the five sample journeys. The samples carry simulated subscription, device and login signals.
- **Bug icon:** shows what the engine decided on each turn (extracted facts, rules that fired, questions asked, signals released).

## Reproduce our results

**No API key needed** (in the repository root):
```powershell
python -m pytest -q tests
python simset/eval/evaluate.py --cases simset/data/dev/cases.jsonl --submission runs/20261108-001633_final_dev_588_single/predictions.jsonl
python simset/tools/validate.py --submission test_predictions.jsonl
```
These run the unit tests (57, LLM mocked), score our final dev run with the organisers' evaluator (86.6 % safe-action pass), and check the submission file covers all 335 test inputs.

**With an API key:**
```powershell
python scripts/run_single.py --cases simset/data/dev/cases.jsonl --mode single --workers 10
python scripts/run_single.py --cases simset/data/test/inputs.jsonl --mode single --workers 10
python scripts/run_single.py --cases simset/data/dev/cases.jsonl --mode multi --workers 10
```
The first two produce the dev result and the test predictions. The third (optional) runs conversations with the organisers' simulated user. Each run writes a folder under `runs/`.

- **Time and cost:** a full dev run takes about 30 minutes with 10 workers and costs roughly $1 in model fees.
- **Concurrency:** lower `--workers` if your API plan limits it.

`test_predictions.jsonl` comes from `runs/20261108-000431_test_335_single_v3`.

## Troubleshooting

| Problem | Fix |
|---|---|
| `'vite' is not recognized` | The frontend packages are not installed. Run `npm install` in the `frontend` folder. Check `node -v` is 20 or newer. |
| `FEATHERLESS_API_KEY is not set` | Create `.env` from `.env.example` in the repository root and add your key. |
| `No module named 'assistant'` | Start the backend from the repository root, not from inside `assistant/` or `frontend/`. |
| The chat says the assistant is unavailable | The backend is not running or cannot reach the API: check terminal 1 for errors. |

## Limitations

- The safety rules were tuned on dev-set failures, and 9 scenario families appear only in the test set, so test performance may be lower than the dev numbers.
- Weakest areas: small-business incidents (74 % pass, 85 % escalation recall) and "twin" cases, where the right answer depends on a fact only the user knows (71 %).
- Free-text chat has no pre-collected signals: in a real deployment they would come from systems such as subscription events and account logins, which this prototype cannot reach. Only the sample journeys carry simulated signals, so the consent step only appears there.
- The simulated user is cooperative; real users are vaguer. Beyond the simulator, we only tested informally with a few other hackathon participants.
